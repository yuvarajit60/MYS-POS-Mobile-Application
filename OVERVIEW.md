# Amsel Mobile — What This Application Does

Companion mobile app for **SRI SELVANAYAKIAMMAN EARTH MOVERS (AMSEL)**, built for field
sales staff to capture sales orders, manage customers/products, and view sales reports from
a phone — writing into the same SQL Server database the desktop AMSEL.INVENTORY ERP uses,
so office staff see the same data with no re-entry.

It is two projects under this folder:

- **`amsel_mobile/`** — the Flutter app (Android/iOS), displayed on-device as **Amsel**.
- **`AMSEL.MOBILEAPI/`** — an ASP.NET Core Web API that sits between the phone and the
  database (phones can't connect to SQL Server directly), documented for deployment in
  [`AMSEL.MOBILEAPI/DEPLOYMENT.md`](AMSEL.MOBILEAPI/DEPLOYMENT.md).

## Sign in

- **Returning user**: the app silently exchanges a stored refresh token for a new access
  token on launch and drops straight onto the landing page — no login screen shown
  (`lib/main.dart`'s `_BootGate`).
- **Username/password**: standard login against the same `USERS` table the desktop app
  uses.
- **First-time / forgot-password — mobile OTP**: enter the mobile number on file
  (`EMPLOYEE.MOBILENO`, looked up in reverse — not the username), receive a 6-digit code by
  SMS, enter it to sign in. If SMS delivery itself fails, the code is still generated
  server-side and the user can proceed with a code obtained from an administrator.

## Landing page

Company name/branding is pulled live from `dbo.COMPANY` (shown pre-login too, never
hardcoded). Four tiles:

- **Create Sales Order**
- **Reports**
- **Customers** (manage)
- **Products** (manage)

## Create Sales Order

Writes to `dbo.SALESORDER` / `dbo.SALESORDER_DETAILS` — the same **draft order** tables the
desktop app's Sales Order screen uses (not the final `SALES` invoice tables; office staff
convert an order to an invoice later, same as today). `ENTRYNO` is generated by the same
`SP_GENERATETRANNO` stored procedure the desktop app calls, so mobile orders continue the
same numbering sequence.

- **Customer** picker: search by name/mobile; if there's no match, an **Add New Customer**
  button appears in that empty state.
- **Site Delivery**: free-text shipping address for the order.
- **Product** picker: search products directly from `dbo.PRODUCT`; same no-match →
  **Add New Product** button.
  - No stock-availability check is required to add a product to an order (that check is
    deferred to the desktop-side conversion step).
  - MRP is editable per line. CGST/SGST are computed from the product's tax % and added to
    MRP for display.
  - Grand total is rounded to the nearest rupee on save.
- Line items grid: qty/rate editable per row, running total, delete a line.
- **Save and Close** posts the order and returns the new `ENTRYNO`.

## Manage Customers / Manage Products

Search-and-list screens reachable from the landing page:

- Tap a row to open it in edit mode (pre-filled form) — save changes or **Delete**.
- Delete is a soft delete (`STATUS = 0`), matching the desktop app's convention — records
  aren't hard-deleted.
- **Add New Product** requires Product Name, MRP, Product Group, Brand, Type, and Sales
  GST %, and writes to both `dbo.PRODUCT` and `dbo.PRODUCT_DETAILS`.
- Creating a product/customer with a name that already exists is rejected (409 Conflict)
  instead of silently duplicating it.

## Reports

- **Summary**: list of sales orders, filterable by Customer, Sales Order No (picked from
  real `SALESORDER.ENTRYNO` values, not free text), and a date range.
- **Details**: tap a Summary row to drill into that order's full line items — not a
  separate top-level filter.
- **Print**: renders an A4 PDF (company + customer letterhead details) and hands it to the
  device's native print system.
- **Graph**: bar chart of sales, grouped Monthly or Yearly.

## Backend API surface (`AMSEL.MOBILEAPI`)

| Area | Endpoints |
|---|---|
| Auth | `POST /api/auth/login`, `POST /api/auth/refresh` |
| OTP | `POST /api/otp/request`, `POST /api/otp/verify` |
| Customers | `GET /api/customers?search=`, `GET/{id}`, `POST`, `PUT/{id}`, `DELETE/{id}` |
| Products | `GET /api/products?search=`, `GET/{id}`, `POST`, `PUT/{id}`, `DELETE/{id}` |
| Sales Orders | `POST /api/sales-orders` |
| Reports | `GET /api/reports/sales-orders/summary`, `GET/{id}`, `GET/graph`, `GET/entry-numbers` |
| Lookups | `GET /api/company`, `/api/brands`, `/api/cities`, `/api/product-groups`, `/api/types` |

JWT bearer auth; `LOCATIONID`/`USERID`/`EMPLOYEEID` are embedded as claims at login/OTP time
so every later query is scoped server-side to the caller's location.
